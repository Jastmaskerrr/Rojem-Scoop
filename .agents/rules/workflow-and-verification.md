# Rojem-Scoop 工作流与验证标准

## 1. 任务实施流程

### 修改前准备
1. 阅读任务涉及的清单文件和相关脚本。
2. 解压或分析应用安装包文件结构，猜测判断可能需要持久化的文件或目录，确认 `persist` 目标文件是否存在。若为运行后动态生成的配置文件，须规划 `pre_install` 建立空文件逻辑（使用 `New-Item -Force` 确保自动创建父级目录）。
3. 在最终将清单写入 bucket 之前，必须在 Artifact 中使用无序列表向用户列出各 Scoop Manifest 字段，等待用户确认后方可执行写入。
4. 确认工作分支基于最新远程主分支。

### 根据修改规模执行
- **小型修改（单个清单新增/更新）**：在获得用户确认清单内容后执行写入，修改后运行测试与格式化。并在添加或更新清单后，同步更新 `README.md` 的应用列表。
- **中型修改（多个清单或脚本联动）**：先分析清单间的依赖关系（`suggest`、`depends`），形成修改计划，再逐个实施并验证。
- **大型修改（架构或通用模式变更）**：必须先分析现状并形成方案，严禁直接大规模删改，需要分阶段实施验证。

## 2. 验证完成标准

任务只有在满足以下全部条件才视为完成：

1. 清单 JSON 格式正确（无报错）。
2. 全部相关测试通过（无报错）。
3. 未修改与任务无关的文件。
4. 无遗留的临时测试代码或多余调试输出。
5. （若涉及清单增删）`README.md` 应用列表已同步更新。

## 3. 验证命令列表

在本地执行验证（使用 `pwsh` 或 `powershell` 运行）：

```powershell
.\bin\formatjson.ps1    # JSON 格式化验证 (必须执行)
.\bin\test.ps1          # Pester 核心逻辑测试 (必须执行)
.\bin\checkver.ps1      # 单个或全局清单版本检测
.\bin\checkhashes.ps1   # 校验哈希值
.\bin\checkurls.ps1     # 检查可达性
```

## 4. 决策优先级

在遇到冲突或难以选择时，遵循以下优先级处理原则：

1. **复用现有验证模式**：优先复用其它清单中已成功验证的设计和架构。
2. **保持整体风格**：维护整个仓库现有范式。
3. **最小化修改**：严格控制改动范围。
4. **规则冲突解决顺序**：用户当前任务明确要求 > 本文件规则 > 项目中其他文档 > Agent 默认实践。
